# ia-taxonomy

対象コンテンツと語を、概念IDを持つ統制語彙と分類体系にまとめる。どのページをどこに置くか、メニューに何を出すかは決めない。

記録の共通規則は [references/records.md](references/records.md) にある。

## 必須入力

- 問題定義（`problem-definition.md` のART-IDと版）。
- コンテンツインベントリ（`content-inventory.yaml`）、または対象概念の一覧を登録した入力。概念一覧の課題では、候補語の各行をインベントリの項目として登録しておく（ia-analysisの手順3）。

インベントリと問題定義が `stale` なら使わない。足りなければia-analysisで作るか、既存の成果物の提供を求める。必須入力がそろうまで、語彙・分類体系は下書きも作らない。足りない入力と、作成を担当するSkillを示して止める。

## 使う知識

| 知識 | 使う場面 |
|---|---|
| KN-002 同名異義語の区別 | 手順2。同じラベルで意味の異なる語を別の概念に分ける |
| KN-003 同義語と表記揺れの統合 | 手順2。優先ラベルの選び方、同義語のまとめ方 |
| KN-004 階層関係と関連関係の区別 | 手順3。上位・下位と関連の区別、複数の上位概念 |
| KN-005 ラベルの命名と粒度の一貫性 | 手順3・4。兄弟項目の観点と粒度、利用者の語 |
| KN-006 ファセット分類 | 手順4。独立した属性で絞り込む体系の設計 |
| KN-013 階層の循環の禁止と複数の上位概念 | 手順3。上位・下位関係を有向グラフとして循環を検査する |
| KN-014 組織化の原則の明文化と要件の対立の扱い | 手順2。入力どうしの食い違いを当事者ごとの要件として記録し、解決の方法を残す |

各知識の「適用条件」を案件の条件と照らし（KN-016 文献の適用条件と案件の条件の照合）、合わない場合はその知識を根拠に使わない。適用条件の対応は判断の `rationale` か `assumptions` に書く。

## 手順

### 1. 語と意味を集める

インベントリの項目、入力の属性列、情報監査の同名異義語・同義語・矛盾の候補から、語とその意味を集める。語ごとに入力の位置子を控える。

### 2. 概念に分ける

`controlled-vocabulary.yaml` に概念を登録する。

- 1つの意味に1つの `concept_id`（`CONCEPT-001` から）を付ける。ラベルを識別子にしない。
- 同じものを指す別の語（同義語、表記揺れ、外来語）は、1つの概念の `alt_labels` にまとめる。優先ラベル（`pref_label.ja`）は利用者が使う語から選び、選んだ理由を判断に残す。英語ラベル（`pref_label.en`）は必要な場合に付ける。
- 同じ語で意味の違うもの（同名異義語）は別の概念に分ける。各概念の `scope_note` に、何を指し何を指さないかを書く。
- 各概念の `sources` に、その概念を確かめた入力の位置子を書く。
- 入力どうしで意味や位置付けが食い違う場合は、両方の位置を観察として判断に記録し、採った方と理由を書く。採らなかった方は `counter_evidence` に挙げ、解決の状況を書く。片方だけを示して関係を決めない。

### 3. 関係を付ける

- 上位・下位関係（`broader`）は、下位概念が上位概念の一種・一部である場合に限る。上位・下位関係は循環させない。
- 種類や部分の関係でない結び付きは関連関係（`related`）にする。関連関係の相互参照は許容する。
- 複数の上位概念を持たせる場合は、採用理由と関係の意味を判断に記録する。
- 事業者が扱わないもの、対象外の語も、利用者が検索に使う語であれば概念として残し、`scope_note` に扱わないことを書く案がある。語彙から外す場合はインベントリで `excluded` にし、理由を書く。

### 4. 分類体系の案を作り、比べる

`taxonomy.yaml` に分類体系（`schemes`）を書く。体系の種類は、独立した属性で絞り込む `facet`、1つの観点の木 `hierarchy`、並列の一覧 `list` から選ぶ。

少なくとも2つの案を作り、[templates/classification-options.md](templates/classification-options.md) に沿って `classification-options.md` で比べる。比較の観点は、問題定義の主要タスクと利用者、カテゴリの重複・不均衡・曖昧さ、兄弟項目の観点と粒度、拡張のしやすさとする。採った案を判断に記録し、退けた案を `alternatives` に書く。各体系の `decision_ref` にその判断のIDと版を書く。

同じ親の下、または同じファセット内の項目は、同じ観点と粒度でそろえる。地区とサービス種別のように別の観点の項目を同じ親の下に混ぜない。

### 5. コンテンツを分類する

`assignments` に、インベントリで `placed` の全項目を、体系の最上位概念からたどれる概念へ割り当てる。複数の概念への割り当て（例: サービス種別と地区）は許容する。

- 分類できない項目、分類の対象外にする項目は、インベントリの区分を `unprocessed`・`excluded` に変えて理由を書き、インベントリの版を上げて登録し直す。
- 概念一覧の課題では、`placed` は「概念の優先ラベルまたは同義語として扱った」ことを表す。

### 6. 登録して検査する

```text
uv run --locked iakit run artifact runs/<run_id> controlled-vocabulary.yaml --kind controlled_vocabulary
uv run --locked iakit run artifact runs/<run_id> taxonomy.yaml --kind taxonomy
uv run --locked iakit run artifact runs/<run_id> classification-options.md --kind classification_options --depends <問題定義のART-ID> <語彙のART-ID> <分類のART-ID>
```

`uv run --locked iakit contracts check runs/<run_id>` は、概念の参照切れ、上位・下位関係の循環、`scope_note` のない同名異義語、未分類の `placed` 項目、現行でない判断の参照を検出する。すべて直してから次へ進む。

ia-orchestratorを使わずに単独で実行していて `iakit` を使えない場合は、`uv run <このSkillのディレクトリ>/scripts/check_artifacts.py <成果物のディレクトリ>` で、同梱したスキーマによる形式検査を行い、通るまで直す。この検査は参照や依存の整合を確かめないため、報告には形式検査の結果を書き、契約検査は `not_run` とする。

### 7. 図にする（任意）

利用者が図を求めた場合、または分類案の比較に図が要る場合は、ホストに外部Skill `diagram-design` が導入されていれば、検査を通った版の分類体系を図にする。導入されていなければ図は作らず、報告に「図は未作成（diagram-design未導入）」と書く。

- 上位・下位関係は体系ごとに `tree` で描く。ファセットは体系ごとに別の木にし、1本の木に混ぜない。概念は優先ラベルと概念IDを併記する。
- 図は `runs/<run_id>/figures/` に置き、元にした分類体系のART-IDと版を図中に書く。分類体系が `stale` になったら図も作り直す。
- 図は派生物であり、成果物として登録しない。判断・契約検査・評価の根拠には `taxonomy.yaml`・`controlled-vocabulary.yaml` を使う。
- diagram-designの出力は閲覧時にGoogle Fontsを読み込む。機密区分の付いた案件では、フォントの読み込みを外したシステムフォントの出力にする。

## 次の段階へ渡すもの

語彙と分類体系のART-IDと版、採った分類案の判断（`IA-nnn rN`）、ナビゲーションで扱うべき論点（例: 複数の入口が要るファセット、同名異義語の表示上の区別）をia-structureへ渡す。タクソノミーの経路ではia-evaluationへ渡す。
