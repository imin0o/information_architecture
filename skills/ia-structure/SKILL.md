# ia-structure

分類と語彙をもとに、コンテンツの配置と探索経路を決める。概念の定義、同義語、上位・下位関係は変えない。変える必要があれば、理由を添えてia-taxonomyへ戻す。

記録の共通規則は [references/records.md](references/records.md) にある。

## 必須入力

- 問題定義（主要タスクと到達先の条件を含む）。
- 統制語彙と分類体系（`controlled-vocabulary.yaml`・`taxonomy.yaml`）。
- コンテンツインベントリ。

どれかが `stale` なら使わない。足りなければ担当Skill（問題定義とインベントリはia-analysis、語彙と分類体系はia-taxonomy）で作るか、既存の成果物の提供を求める。必須入力がそろうまで、サイトマップ・構造の案は下書きも作らない。足りない入力と担当Skillを示して止める。

## 手順

### 1. 構造の種類を選ぶ

主要タスクと分類体系から、階層、ネットワーク（リンク）、ファセット（属性による絞り込み）のどれを組み合わせるかを決める。少なくとも1つの代替構造を検討し、退けた理由とともに判断に記録する（`stage: structure`）。

複数の属性で絞り込むタスクがある場合は、どの属性から入っても到達先に着けることを条件にする。1つの属性だけの階層にすると、別の属性から探す利用者が全件を見なければならなくなる。

### 2. サイトマップを書く

`sitemap.yaml` にノードを書く。

- 各ノードに `node_id`（`NODE-001` から）を付ける。ルートは1つで、`parent: null` はルートだけにする。
- 親子関係（`parent`）は階層を、`links` は親子以外の移動（関連ページ、ファセットの絞り込み結果への移動、料金や申込みへの横の移動）を表す。どちらを使ったかを区別する。
- ノードが概念を表す場合は `concept_id` を書く。ナビゲーションの表示ラベルは概念の優先ラベルを基本とし、文脈に合わせて別の表示にする場合は理由を判断に記録する。
- インベントリで `placed` の全項目を、少なくとも1つのノードの `content_ids` に置く。`excluded`・`unprocessed` の項目は置かない。
- 同じコンテンツを複数のノードに置くこと（地区の入口とサービス種別の入口の両方など）は許容する。

### 3. 主要タスクの経路を書く

`tasks` に、問題定義の主要タスクごとに、ルートから到達先までのノード列を書く。隣り合うノードは、親子関係かリンクでつながっていなければならない。経路が到達先の条件を満たすことを、`information-architecture.md` で説明する。

### 4. 構造の説明を書く

[templates/information-architecture.md](templates/information-architecture.md) に沿って `information-architecture.md` を書く。構造の種類と採用理由、代替構造、ナビゲーションラベルと概念の対応、主要タスクの経路、意図的な例外（孤立ノード、循環するリンク、対象外のコンテンツ）を示す。重要度の高いタスクの経路が短くなっているかも書く。

### 5. 登録して検査する

```text
uv run --locked iakit run artifact runs/<run_id> sitemap.yaml --kind sitemap
uv run --locked iakit run artifact runs/<run_id> information-architecture.md --kind information_architecture --depends <問題定義のART-ID> <サイトマップのART-ID>
```

`uv run --locked iakit contracts check runs/<run_id>` は、到達できないノード、参照切れ、親子の循環、未配置の `placed` 項目、つながっていない経路を検出する。すべて直してから次へ進む。

ia-orchestratorを使わずに単独で実行していて `iakit` を使えない場合は、`uv run <このSkillのディレクトリ>/scripts/check_artifacts.py <成果物のディレクトリ>` で、同梱したスキーマによる形式検査を行い、通るまで直す。この検査は参照や依存の整合を確かめないため、報告には形式検査の結果を書き、契約検査は `not_run` とする。

## 戻す場合

配置の検討中に、概念の分け方や上位・下位関係の不備が分かった場合は、サイトマップで回避せずにia-taxonomyへ戻す。戻した結果、語彙や分類の版が上がると、サイトマップは `stale` になる。再生成してから登録し直す。

## 次の段階へ渡すもの

サイトマップと構造の説明のART-IDと版、主要タスクの経路、未検証の前提（例: 利用者がどの入口から探し始めるか）をia-evaluationへ渡す。
