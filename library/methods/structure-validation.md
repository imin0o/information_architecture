# 構造とラベルの検証方法

分類、ラベル、ナビゲーションの判断を、利用者を対象にした調査で確かめる方法である。ia-evaluationで検証計画を作るときに使う。

## 手順

1. 組織化の方式の好みを利用者に直接尋ねない。多くの利用者は情報アーキテクチャを説明する語彙を持たず、意味のある答えが得られないため、行動を観察する方法を使う [CLAIM-0043]。
2. 分類やラベルの候補を探す段階では、自由なカードソートで利用者のまとめ方と名付け方（メンタルモデル）を調べる [CLAIM-0044]。
3. 作った構造を確かめる段階では、定義済みのラベルとカテゴリを使う閉じたカードソートを使う。自由と閉じたの間は目的に応じて調整する [CLAIM-0044] [CLAIM-0045]。
4. ナビゲーションは、利用者に情報を探すかタスクを完了してもらうユーザーテストで確かめる。考えを声に出してもらい、発言と移動先を記録する [CLAIM-0046]。
5. 参加者にはサイトに慣れた人と慣れていない人を含め、課題は調査の目的に沿って明確に定める [CLAIM-0047]。

## 適用条件

- 手順2と3は、分類やラベルの候補を探す、または検証する場合に使う [CLAIM-0044]。
- 手順4と5は、構造やナビゲーションを利用者で確かめる場合に使う [CLAIM-0046] [CLAIM-0047]。

## 代表ケースとの対応

ルーブリックR-07の「検証計画に、未検証の判断と確かめる方法を対応付けている」に対応する。代表ケースはどちらも実ユーザー調査の記録がないため、構造の判断を tested_* にせず、未検証の判断ごとに手順2〜5のどれで確かめるかを検証計画に書く。主要タスク（TASK-01〜04など）は、手順4のユーザーテストの課題にそのまま使える。

## 仮説・補完

次の内容は登録済みの文献主張に基づかない。

- ツリーテスト（ラベルと階層だけを示して到達先を選んでもらう方法）は、BOOK-001の読んだ範囲には出てこない。手順4のナビゲーションの検証を、見た目を除いて行う方法として候補にできるが、根拠の登録が必要である。BOOK-010（Card Sorting）は未受領である。
- LLMによる模擬評価は、手順1〜5の利用者調査の代わりにならない（ルーブリックR-07）。
